# ASOC ENGINE — Full Audit (2026-09-28)

Scope: the tree at `aeb1868` (ASOC-quests-chat-lanes), following `Claude outputs/CLAUDE-FULL-AUDIT-PROMPT.txt`.
Read-only audit: no source files were changed. Every test file was run individually in an isolated data dir.
Line numbers refer to `aeb1868`.

---

## A. Executive summary

- **Tests: 51 files, 50 pass, 1 deterministic failure** (`tests/battle-flow.js:217`). `npm test` stops at the first failure, so as wired it reports **red**.
- **No CI runs the suite.** The only workflow builds the desktop installer, and Railway deploys `main` without running tests. A red suite can ship today.
- **Core game logic is in good shape.** GM authorization is enforced on all 44 `gm:*` handlers. Player identity comes from the server-side auth token. The Shadow Coin ledger is integer-based and idempotent. The remote-image fetch resists SSRF. Client rendering escapes consistently.
- **The main risks are availability and scale, not correctness:**
  1. A player can fill the `/data` volume (unthrottled 5 MB uploads, never deleted). A full volume trips persistence failure and disconnects everyone.
  2. Player login and registration run a ~105 ms synchronous PBKDF2 with no rate limit, so a small request flood freezes every live game.
  3. Every chat message rewrites and fsyncs the whole recovery file. That file holds a copy of the sender's avatar on every message, plus every player who has ever joined. Measured at **14 MB and about 160 ms blocked per chat message**.
- **One real gameplay hazard:** in CASUAL display the battle clock keeps running and can declare GAME LOST, while chat in CASUAL can't score.
- **Verdict: stable, with known issues.** Details in section G.

## B. Findings

### HIGH

#### H1. Unbounded chat uploads can fill the data volume and take the server down
- **Symptom:** any logged-in Little Hero can POST `/api/chat/image` (or `/api/chat/image-url`) as fast as they like. Each upload is up to 5 MB and lands in `/data/chat-uploads/` permanently.
- **Root cause:**
  - The HTTP upload routes (`server.js:8902`, `server.js:8925`) have no rate limit. The WebSocket chat cooldown (`PLAYER_CHAT_MIN_INTERVAL_MS`) does not apply to them.
  - `persistChatImage` (`server.js:5270`) writes files that are never deleted. The only `unlinkSync` in the project removes `.tribute` marker files (`server.js:1383`). Files stay on disk after their message drops out of the 200-message history, and after the message is deleted.
- **Impact:** once the volume is full, the next durable write fails. `failPersistence` then makes every WebSocket message close the socket with `1013 Storage unavailable` (`server.js:9564`). That is a full outage, and it needs manual disk cleanup.
- **Fix direction:**
  - Add a per-player token bucket on both HTTP upload routes.
  - Add a global disk budget, and refuse uploads above it.
  - Add a sweeper that removes uploads whose URL no longer appears in any room's chat history, keeping tribute-vault references.

#### H2. Player login and registration can freeze the whole server
- **Symptom:** a burst of `/api/auth/player/login` or `/register` requests stalls every game: timer ticks, chat, and board commands.
- **Root cause:**
  - `auth-store.js:67` uses `pbkdf2Sync` with 210,000 iterations, measured at **~105 ms per call**, on the main thread.
  - There is no throttling on player `login` (`server.js:9109`), `register` (`server.js:8984`) or `reset-password`. The GM login has a lockout, but it doesn't apply here.
  - `login()` returns immediately for an unknown email (`auth-store.js:102`), so response time reveals whether an account exists.
- **Fix direction:**
  - Switch to async `crypto.pbkdf2`, or `scrypt` via its callback form, so hashing leaves the event loop.
  - Add per-IP and per-account attempt limits.
  - Hash against a dummy salt when the email is unknown, so both paths take the same time.

#### H3. Recovery persistence is O(everything) per event and blocks the event loop
- **Symptom:** chat lag grows as the community and chat history grow.
- **Root cause:**
  - `persistActiveRooms()` (`server.js:382`) runs on every chat message, reaction, vote and so on. Each call re-serializes the whole room and writes it with fsync.
  - The room includes `room.chat` verbatim (`server.js:359`). `addChatMessage` stores a copy of the sender's `avatarData`, up to 200 KB, on **every message** (`server.js:5421`). Those per-message copies aren't sent to clients (`getChatState` omits them).
  - Nothing reads them back except the tribute sender avatar (`server.js:1354`), and that one could come from the live player record instead.
  - `commandReceipts` (up to 2048 entries) and the full `gameData` also go into every write.
- **Evidence:** a synthetic room with 200 messages, 40 players and 60 KB avatars produced a **14.4 MB file at ~160 ms per synchronous write**, on local disk. A network volume on Railway will be slower.
- **Fix direction:**
  - Stop storing `avatarData` on chat messages; resolve it from the player id at render time.
  - Coalesce persistence: mark the room dirty and flush at most every 250–500 ms, keeping the synchronous flush for terminal or authoritative transitions.
  - Before any of this, keep the "visible ⇒ persisted" contract in `handleChatGuess` (`server.js:7691`) in mind. Debouncing changes that guarantee, so decide it explicitly.

#### H4. The battle clock keeps running in CASUAL and can declare GAME LOST
- **Symptom:** the GM toggles to Amusement Park mid-battle. The clock keeps draining, enters Borrowed Time, and `declareGameLost` fires: FINAL red, −200 penalties, WOMF +3. Players are on the casual surface and **cannot score**.
- **Root cause:**
  - `handleSetRoomMode` (`server.js:8699`) is documented as "presentation-only" and never pauses the timer.
  - The global tick (`server.js:2626`) ignores `roomMode`, although `enterBorrowedIfAllColumnsOpen` does check for `BATTLE` (`server.js:2603`), which is inconsistent.
  - `addChatMessage` stamps `boardId: null` outside BATTLE (`server.js:5429`), so any guess sent in CASUAL can never be adjudicated.
- **Fix direction:** this is a product decision. Either
  - (a) auto-pause the clock (`paused` / `borrowed_paused`) and solution countdowns on entering CASUAL, and resume on return; or
  - (b) block the CASUAL toggle while the clock is live.

  Add a test either way.

#### H5. The test suite is red and nothing gates deploys
- **Failing:** `tests/battle-flow.js:217`, "hiding a GM-revealed Final resumes play": expected `running`, got `borrowed`. It fails the same way on every run.
- **Root cause:** two rules added together in `b805567` conflict:
  1. `revealAll` (`server.js:3424`) reveals A5–D5 and stops the clock.
  2. `hideFinal` (`server.js:3476`) resumes it to `running`.
  3. Within one second, `enterBorrowedIfAllColumnsOpen` (`server.js:2600`) sees all four column solutions on the board and forces Borrowed Time.

  Whether this is a test bug or a runtime bug depends on intent. Should *GM-revealed* column solutions count as "all columns open"? Today they do, so REVEAL ALL → HIDE FINAL silently starts a 2:00 sudden death.
- **Process gap:**
  - `.github/workflows/desktop-release.yml` is the only workflow.
  - Railway deploys on push (`railway.json`).
  - `npm test` is a chain of `&&` commands, so one failure hides every later file.
- **Fix direction:**
  - Decide the rule. A likely-correct version: only count columns that are solved, failed, or revealed by players, or skip the borrowed switch while `stoppedFrom` was set by a GM reveal.
  - Add a GitHub Actions workflow that runs `npm test` on push and PRs.
  - Make `tests/run.js` (or a new runner) run every file and report all failures.

### MEDIUM

#### M1. `room.players` never shrinks, and each `players:update` is O(all players ever) with avatars
- **Root cause:**
  - The only `room.players.delete` replaces a socket for the *same* id (`server.js:6707`). Disconnected heroes stay forever by design ("stable reconnect identity") and survive restarts (`serializeRoomForRecovery`).
  - `getPlayersSnapshot` (`server.js:6786`) does a synchronous full read and parse of `players.json` on every broadcast, then sends every player's `avatarData` (up to 200 KB each) to every client.
  - Broadcasts happen on joins, purchases, spins, equips, relics, quests and IKS.
- **Fix direction:**
  - Prune offline identities after N days, and keep scores in `room.scoring`.
  - Send avatars once per player plus a hash, rather than on every update.
  - Cache the parsed `players.json` in memory, since the store is single-process anyway.

#### M2. A failed quest reward still consumes the quest
- **Where:** `handleGmQuest` (`server.js:6149`) calls `questEngine.transition(..., 'COMPLETED')` **before** `awardShadowCoins`.
- **What happens:** `transition` moves the quest to history. If the award fails (for example, player storage is unhealthy), the handler returns an error, but the quest is already COMPLETED in memory with `rewardReceipt: null`. The next persist saves it that way, and nothing can retry it.
- **Fix direction:** award first. The receipt `quest:<id>:reward` is already idempotent, so retries are safe. Only transition after the award succeeds.

#### M3. The "once" +10 Shadow Coin grant runs on every boot
- **Where:** `server.js:115`. `grantAllShadowCoins` runs at every process start.
- **What happens:** the receipt stops a profile from being granted twice. But any profile created **after** the first boot gets +10 SC at the next deploy or restart. With email verification off (`ASOC_EMAIL_VERIFICATION=0`) and no registration limit, new accounts effectively mint coins on every deploy.
- **Fix direction:**
  - If the intent was "accounts that existed on 2026-09-28", add a `createdAt` cutoff or a one-shot marker file in `/data`.
  - If it was "every account forever", move it into account creation.
  - Either way, remove admin one-offs from module top level.

#### M4. The GM login lockout is permanent and keyed on a spoofable header
- **Where:** `gmClientKey` (`server.js:598`) and `/api/auth/gm/login` (`server.js:9213`).
- **What happens:**
  - Three bad attempts lock that client key **forever**. Only editing `/data/gm-lockouts.json` undoes it, and the file grows without limit.
  - With `ASOC_TRUST_PROXY=1`, the key is the **leftmost** `X-Forwarded-For` value, which the client controls when the proxy appends rather than overwrites.
  - So an attacker could rotate XFF to get unlimited password guesses. An attacker could also lock out the Shadow Broker, if they send the GM's own IP as XFF and the proxy appends.
- **Fix direction:**
  - Use the rightmost entry added by the trusted proxy (Railway's hop).
  - Replace permanent lock with an exponential time-based backoff.
  - Verify how Railway's edge actually sets XFF.

#### M5. The player contract overlay re-renders every second
- **Where:** `js/player-quests.js:4`. `render()` runs on a 1 s interval and calls `open(q)`, which replaces `overlay.innerHTML` while the overlay is open.
- **What happens:** a press that straddles a re-render loses its click (ACCEPT, DECLINE, CLAIM). Focus and hover state also reset every second. The file is a single minified line, which makes review hard.
- **Fix direction:** render the shell once and update only the timer text node. Un-minify the file.

### LOW

- **L1. No security headers.** There's no CSP, `X-Content-Type-Options: nosniff`, `frame-ancestors`/`X-Frame-Options`, or `Referrer-Policy` anywhere in `server.js`. The GM panel can be framed (clickjacking). Uploaded images are served without `nosniff`.
- **L2. No compression.** `join.html` is 422 KB, with about 8,800 lines of inline CSS and 23 inline data-URIs. It's served `no-store` without gzip or ETag on every load, which is expensive on mobile.
- **L3. The cache-bust commits do nothing for browsers.** HTML, JS and CSS are already `no-store` (`server.js:9401`). The manual `?v=` bumps (45 in `join.html`, 41 in `index.html`) only matter for `CLIENT_BUILD` (`server.js:92`), which reads just the `player.js` and `app.js` versions. That explains the many "Bust cache" commits. Derive the build id from a content hash or the deploy SHA instead.
- **L4. Two tests are never run by `npm test`:** `tests/chat-media-context-menu.js` (added in the latest commit) and `tests/unstable-concoction.js`. Both pass when run on their own.
- **L5. Poll payloads carry avatars.** `getChatState` includes every poll voter's `avatarData` (`server.js:6491`) and is broadcast to everyone on every chat update.
- **L6. Roulette odds are inconsistent.** A straight bet pays 12:1 on 13 pockets, which has an expected value of **0**. All other bets have an expected value of −1/13, and the comment says 0 is the house number. Harmless, since coins are cosmetic-only, but not what the design states.
- **L7. `npm audit`:** 2 moderate findings (`exceljs` → `uuid`). The affected path is the GM-only XLSX import/export.
- **L8. Repo hygiene:**
  - About 36 MB of design binaries sit at the repo root: `Asoc forever 2 copy.tif` is 27 MB, plus PNGs and an xlsx.
  - `games/kurac-test.json` is a test game committed to the library.
  - `HANDOFF.md` has mojibake (`â€”`, `Ã—`).
- **L9. Split escaping helpers.** There are about 10 separate `esc` implementations across `js/*`. They are all correct today; a shared helper would prevent drift.

### Checked and found sound
- **GM authorization:** every `gm:*` handler checks `ws === room.hostConnection`, and `hostConnection` is only assigned after `isValidGmToken`.
- **Identity:** a player's id is always the server-side auth account. Client-supplied ids are ignored. A newer socket supersedes the older one.
- **Shadow Coins:**
  - Integer tenths with idempotent receipts.
  - Purchases are priced and validated on the server.
  - Balances never go negative.
  - Each roulette spin is settled in a single ledger write.
- **Remote image import:** DNS is resolved once and pinned to a public address, ports are fixed to 80/443, redirects are bounded, size is capped, and file signatures are checked.
- **Static serving** is allowlisted.
- **Message caps:** `maxPayload` is set on the WebSocket server, and there's a per-socket message token bucket.
- **Client rendering:** no unescaped player-controlled strings were found in `innerHTML` templates.
- **Old "known anomaly":** the `production-readiness.js` failure described in the old audit prompt **no longer reproduces**. It passes with isolated data dirs.

## E. Test gaps: five highest-value tests to add

1. **CASUAL during a live clock.** Toggle to CASUAL with the clock running and a short `ASOC_TIMER_BORROWED_MS`. Assert whatever H4 decides (paused, or toggle refused). Assert no GAME LOST fires while the room is in CASUAL.
2. **Upload abuse.** N rapid `/api/chat/image` POSTs from one player get throttled. Uploads whose messages have aged out are swept.
3. **Quest reward failure.** Put player storage into its unhealthy state and send `gm:questComplete`. Assert the quest stays CLAIMED and can be retried, with no double pay once it succeeds.
4. **Auth flood.** Measure event-loop lag (a `setInterval` drift probe) during 20 concurrent failed logins. Assert lag stays under a bound and the attempts are rate limited.
5. **Persistence size bound.** After 200 chat messages from avatar-bearing players, assert `active-rooms.json` stays under a size budget, and that `players:update` doesn't grow with long-offline identities.

Also: add a CI workflow, wire in the two orphan tests (L4), and make the runner report every failing file.

## F. DO NOT TOUCH (canon)

- Board geometry: fixed 1900×1267 canvas, skeleton placement, difficulty-logo placement.
- Board structure: columns A–D; A1–A4 are clues; A5–D5 are column solutions; the Final is row 6. The story uses A5–D5 and runs about 100 words.
- Progressive Clue Queue: reveal order maps hardest → easiest, whatever the physical slot. `clueOrder` is append-only per board.
- Difficulty tiers: GREEN, YELLOW, AMBER, RED, PURPLE, BLACK.
- Timer: 20 min for GREEN/YELLOW, 25 for AMBER, 35 for RED/PURPLE/BLACK. Borrowed Time is 2:00. `'expired'` is display-only; GAME LOST goes only through `declareGameLost`.
- Scoring:
  - Columns score 400/300/200/100.
  - The Final scores 1200/800/500/300 by columns known.
  - Streak bonuses are +50/+125/+250.
  - A failed Final costs −200 per player.
  - A zero-clue solve resolves with no points.
- WOMF: persistent 0–10. +1 per failed column, +3 for a failed Final or GAME LOST. At 10 the Wheel is ready for a manual roll. The Blood Tribute settles it.
- The permanent MASTER room. Modes are CASUAL, BATTLE_ARMED, BATTLE and RECOUNT (presented as Amusement / Abusement Park). Chat, identities, profiles, themes and reactions persist across modes.
- GM panel order: CHAT first, then clue controls. Chat stays fixed, scrollable and stable through mode changes.
- The server is authoritative for state, timer, scoring, wheel landing and coins. Clients only interpolate.
- Shadow Coins are account-keyed (never by name), use integer tenths, and every change carries an idempotent receipt.
- Production: one Railway replica, `/data` volume, `ASOC_DATA_DIR=/data`, `/health`, direct `node server.js`. Keep `ASOC_EMAIL_VERIFICATION=0` until external email delivery is confirmed.

## G. Final verdict: **stable, with known issues**

Game rules, authorization, identity and the coin ledger are implemented carefully and are well covered by 50 passing test files. Nothing found lets a player cheat the board or mint coins directly.

It is not "stable" outright, for four reasons:
1. The suite is red, and there is no CI gate in front of auto-deploy (H5).
2. Two cheap denial-of-service paths exist, available to any registered player or anonymous visitor (H1, H2).
3. Persistence and broadcast costs grow without limit with community size (H3, M1).
4. A reachable gameplay path produces an unfair GAME LOST (H4).

Suggested order:
1. H5: decide the rule and add CI.
2. H1 and H2: rate limits and async hashing.
3. H4: decide CASUAL clock behaviour.
4. H3 and M1: strip per-message avatars, prune identities.
5. M2 and M3.
